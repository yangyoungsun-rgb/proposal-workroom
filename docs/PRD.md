# 제안서 작성 관리 서비스 PRD

Oct 23, 2026 · @양영선

## 1. 개요

**한 줄 요약**: proposal-full-pipeline 스킬의 P1\~P8 단계를 웹 화면에서 진행하고, 각 단계의 산출물을 미리보고, 검토 의견을 남기고, PM이 승인해야 다음 단계로 넘어가는 "제안 작업실" 서비스를 만든다.

**배경**: 지금은 스킬이 Claude 대화 안에서만 돈다. 산출물(trace.csv, 스토리보드.xlsx, 장표 pptx 등)은 대화마다 흩어지고, "PM이 확인한 뒤 진행이라고 말한다"는 승인도 대화 기록에만 남는다. 작성자가 여럿이고 사업이 동시에 여러 건이면 누가 무엇을 언제 승인했는지 추적이 안 된다.

**범위 (1차)**

- 제안 사업(프로젝트) 등록과 단계(P1\~P8) 진행판
- 단계별 스킬 도구 실행과 결과 저장
- 산출물 미리보기 (엑셀·pptx·pdf·md·hwp)
- 검토 요청, 의견, 수정 요청표
- 단계 게이트 승인과 잠금(킷 잠금, 원고 잠금, 제출본 동결)
- 검증 결과(S0/S1/S2) 대시보드
- 간소 경로(소규모 입찰) 지원

**범위 밖 (1차)**: 나라장터 자동 제출, 가격 제안서 작성, 외부 발주처 계정 연동, 모바일 앱.

## 2. 문제와 목표

스킬이 경고하는 가장 비싼 재작업 세 가지(틀 미잠금, 원고 미잠금, 비식별 늦게 하기)는 모두 "승인과 잠금이 기록으로 강제되지 않아서" 생긴다. 이 서비스는 그 잠금을 화면과 데이터로 강제한다.

| 지금 겪는 문제 | 서비스가 해결하는 방식 |
| --- | --- |
| 산출물이 대화·PC·메일에 흩어짐 | 사업별 저장소 하나, 확정본은 항상 하나(구버전 자동 보관) |
| 승인이 "진행" 한 마디로만 남음 | 단계 게이트마다 승인자·시각·근거 기록 |
| 잠근 원고가 몰래 바뀜 | 잠금 후 수정은 변경 요청표 승인을 거쳐야만 반영 |
| 검증 결과를 매번 전부 다시 읽음 | 직전 대비 바뀐 것·아직 남은 것만 보여주는 차분 보기 |
| 파일을 열어봐야 내용을 앎 | 브라우저 미리보기, 장표 썸네일, 두 버전 나란히 비교 |
| 여러 사업의 진척을 한눈에 못 봄 | 사업별 단계 진행판과 마감 D-day |

**성공 지표 (출시 후 3개월, 목표값은 착수 회의에서 확정)**

- 서비스로 진행한 사업 수: \[확인 필요\]건 이상
- 제출본 S0(제출 불가) 0건 유지율 100%
- 잠금 후 승인 없는 변경 0건
- 마감 하루 전 업로드 완료율
- 작성자 설문 "산출물 찾는 시간 줄었다" 응답 비율

## 3. 사용자와 역할

역할은 사업마다 따로 준다. 한 사람이 A사업에서는 PM, B사업에서는 작성자일 수 있다.

| 역할 | 누구 | 할 수 있는 일 | 할 수 없는 일 |
| --- | --- | --- | --- |
| PM (제안 총괄) | 사업 책임자 | 단계 게이트 승인, 잠금·동결, 변경 요청 승인, 역할 배정 | — |
| 작성자 | 장(章) 담당 | 맡은 장의 원고·장표 작성, 도구 실행, 검토 요청 | 게이트 승인, 잠긴 원고 직접 수정 |
| 검토자 | 사내 선임, 협력사 | 의견 작성, 수정 요청, 검토 완료 표시 | 파일 수정 |
| 모의평가자 | 작성에 참여하지 않은 2\~3명 | 평가표 채점, 지적사항 입력 | 다른 평가자 점수 보기(채점 끝날 때까지) |
| 관리자 | 사업팀 운영 담당 | 사용자·권한, 스킬 버전, 공통 금칙어 관리 | 사업 산출물 승인 |
| 열람자 | 본부장 등 | 진행판·대시보드 보기 | 작성·승인 |

협력사 검토자는 비식별 처리본만 볼 수 있게 제한할지 \[확인 필요\].

## 4. 단계 흐름과 다음 단계로 넘어가기 전 확인

서비스의 뼈대는 스킬의 P1\~P8 그대로다. 각 단계 끝에서 통과 기준을 자동 점검하고, PM이 승인해야 다음 단계가 열린다.

&#91;embedded content: P1\~P8 단계 흐름 · 단계마다 PM 확인, 잠금 3곳\]

승인할 때는 그 순간의 자동 점검 결과가 함께 저장된다. 나중에 "왜 넘어갔나"를 기록으로 확인할 수 있다.

| 단계 | 자동 점검에 쓰는 스킬 도구 | 통과 기준 | 잠금 |
| --- | --- | --- | --- |
| P1 | trace\_matrix.py extract, instructions.py extract | 요구사항 ID 전건 등재, rules·facts `_sample` 제거 | — |
| P2 | strategy\_check.py, storyboard.py check·export | S0·S1 0건, 요구사항 100% 배정, 매수 합 ≤ 상한 | — |
| P3 | deck\_qa.py (데모 3매 렌더) | 데모 검증 통과, 비식별 구조 설계 | 틀 잠금 |
| P4 | `[확인 필요]` 집계, facts.json 대조 | 확인 필요 0건, 수치 전건 일치 | 원고 잠금 |
| P5 | build\_all.py, deck\_qa.py, consistency\_check.py | 빌드 경고 0, 기하 QA 통과 | — |
| P6 | scan\_text.py, trace\_matrix.py check, instructions.py check, review.py check | 제출 불가(S0) 0건, 치명 지적 미결 0건 | — |
| P7 | instructions.py check --final | 수기 확인 항목 미확인 0건 | 제출본 동결 |
| P8 | qa\_bank.py check, tts\_split.py, deck\_qa.py | 리허설 시간이 배정 시간의 ±10% | D-3 내용, D-1 파일 |

**간소 경로**: P1 → P2(핵심 관심사 1\~3개 메모 + 스토리보드) → P3\~P5를 합쳐 PM 검토 1회 → P6 → P7, 발표가 있을 때만 P8. 간소 경로도 세 가지 기준은 똑같이 막는다: 요구사항 전건 대응, 제출 불가 0건, 작성 지시 미확인 0건.

## 8. 시스템 구성과 스킬 연동

스킬을 고치지 않고 그대로 감싼다. 서비스는 스킬 폴더를 사업별 작업 폴더로 복사해 스크립트를 돌리고, 종료코드와 출력 파일을 읽어 화면에 보여준다.

&#91;embedded content: 시스템 구성 · 화면, 서버, 실행기 3종, 저장소\]

**스킬 연동 원칙**

- **스킬이 기준**: 단계 정의, 통과 기준, 등급(S0/S1/S2)은 스킬의 SKILL.md와 스크립트 종료코드를 따른다. 서비스가 기준을 따로 만들지 않는다
- **종료코드 해석**: 0 = 통과, 2 = 제출 불가(S0) → 승인 차단, 3 = 판독 실패(검사 안 됨) → 별도 경고
- **두 가지 작업 방식**: ① 버튼으로 도구를 바로 실행(검증·추출처럼 정해진 작업), ② Claude 대화창에서 스킬과 함께 작업(전략·원고처럼 판단이 필요한 작업). 어느 쪽이든 결과는 같은 저장소에 새 버전으로 쌓인다
- **연계 스킬**: P1 분석 워크북은 rfp-analysis-workbook, PDF 합본은 proposal-pdf-merge, 참여 판정은 project-engagement-assessment를 같은 실행기에서 쓴다
- **버전 관리**: 새 스킬 버전은 관리자가 올리고 selftest.py가 45/45 통과해야 새 사업에 쓸 수 있다. 진행 중인 사업은 시작한 버전을 유지한다
- **외부 반출 최소화**: 스크립트는 사내 실행기에서 돌고, Claude에는 사용자가 대화창에서 고른 파일만 보낸다
